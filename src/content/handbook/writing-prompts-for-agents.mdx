## ทำไมโจทย์ถึงสำคัญ

ลองนึกถึงช่างที่ทำงานเร็วมากและฝีมือดีมาก แต่ไม่เคยเห็นบ้านของเรา ถ้าเราบอกแค่ว่า "ทำห้องครัวให้หน่อย" ช่างต้องเดาทุกอย่าง ตั้งแต่ขนาด สี ไปจนถึงงบประมาณ ผลงานอาจสวยมาก แต่ไม่ใช่ห้องครัวที่เราต้องการ

AI agent ก็เป็นแบบนั้น มันเขียนโค้ดได้เร็วกว่าคน แต่รู้เรื่องงานของเราเท่าที่เราบอกเท่านั้น ทุกช่องว่างในโจทย์คือจุดที่มันต้องเดา และการเดาผิดคือที่มาของงานที่ต้องแก้ซ้ำ

งานของ dev ยุคนี้จึงย้ายจาก "พิมพ์โค้ดทุกบรรทัดเอง" มาเป็น "อธิบายงานให้ชัด แล้วตรวจว่าได้ตามนั้นจริง" มากขึ้น การเขียนโจทย์จึงเป็นทักษะพื้นฐาน ไม่ใช่ทริกลัด

## โจทย์ที่ดีมี 4 ส่วน

| ส่วน | ตอบคำถามว่า | ตัวอย่าง |
| --- | --- | --- |
| **เป้าหมาย** | อยากได้อะไร และเอาไปใช้ทำอะไร | หน้าเว็บจดสิ่งที่ต้องทำ ไว้ใช้เองบนมือถือ |
| **บริบท** | ตอนนี้มีอะไรอยู่แล้ว ใช้เครื่องมืออะไร | ยังไม่มีโปรเจค ใช้ HTML, CSS และ JavaScript ไฟล์เดียว |
| **ขอบเขต** | อะไรที่ไม่ต้องทำ หรือห้ามแตะ | ยังไม่ต้องมีระบบล็อกอิน ห้ามใช้ไลบรารีจากภายนอก |
| **เกณฑ์รับงาน** | ตรวจยังไงว่างานเสร็จ | ปิดแล้วเปิดหน้าใหม่ รายการยังอยู่ |

มือใหม่มักลืม "ขอบเขต" กับ "เกณฑ์รับงาน" แต่สองส่วนนี้แหละที่ทำให้เราคุมงานได้ ขอบเขตกันไม่ให้ agent ทำเกินหรือแตะของที่ไม่ควรแตะ ส่วนเกณฑ์รับงานบอกเราว่าเมื่อไหร่ถึงเรียกว่าเสร็จ

## เกณฑ์รับงานที่ดีหน้าตาเป็นยังไง

หลักง่าย ๆ คือ ถ้าให้คนอื่นอีกคนมาตรวจ ต้องได้คำตอบเดียวกับเรา คำที่แต่ละคนตีความไม่เหมือนกัน เช่น "ง่าย" "เร็ว" "สวย" ใช้เป็นเกณฑ์ไม่ได้

| ตรวจไม่ได้ | ตรวจได้ |
| --- | --- |
| ใช้งานง่าย | ปุ่มทุกปุ่มสูงอย่างน้อย 44 พิกเซล กดด้วยนิ้วโป้งได้ |
| โหลดเร็ว | เปิดหน้าแล้วเห็นรายการภายใน 1 วินาที |
| หน้าตาสวย | สีและตัวอักษรตรงกับภาพตัวอย่างที่แนบมา |
| ไม่มีบั๊ก | ลบรายการหนึ่งแล้ว รายการอื่นยังอยู่ครบ |

## งานใหญ่ ให้แบ่งเป็นรอบ

ถ้าเขียนเกณฑ์รับงานแล้วยาวเกินราว 5–6 ข้อ หรืองานแตะหลายหน้าพร้อมกัน มักเป็นสัญญาณว่างานใหญ่เกินไปสำหรับรอบเดียว ให้แบ่งเป็นรอบเล็ก ๆ ที่แต่ละรอบตรวจได้ เช่น

1. รอบที่ 1: เพิ่มรายการ และแสดงรายการ
2. รอบที่ 2: ติ๊กว่าเสร็จ และลบรายการ
3. รอบที่ 3: จำรายการไว้หลังปิดหน้า

แต่ละรอบเล็กพอให้ตรวจได้ในไม่กี่นาที ถ้ารอบไหนผิด ก็แก้หรือย้อนแค่รอบนั้น ไม่ต้องรื้อทั้งหมด

งานที่เกี่ยวกับเงิน ข้อมูลส่วนตัว หรือการเข้าสู่ระบบ ควรแบ่งให้เล็กที่สุดและตรวจละเอียดที่สุด อ่านต่อใน <ChapterLink number={9} />

</Callout>

## สิ่งที่ต้องบอกทุกครั้ง ให้เขียนไว้ในไฟล์เดียว

บางเรื่องต้องบอก agent ทุกครั้ง เช่น ให้ตอบเป็นภาษาไทย ห้ามแตะไฟล์ที่เก็บรหัสลับ หรือก่อนส่งงานต้องรันเทสต์ แทนที่จะพิมพ์ซ้ำทุกโจทย์ ให้เขียนไว้ในไฟล์บริบทของโปรเจค ซึ่งเครื่องมือหลายตัวอ่านให้เองตอนเริ่มงาน ชื่อไฟล์ขึ้นกับเครื่องมือที่ใช้ เช่น `AGENTS.md` หรือ `CLAUDE.md`

<Callout tone="case" title="เคสจริงจาก MilerDev">

เว็บที่คุณกำลังอ่านอยู่ก็ทำงานแบบนี้ ไฟล์ `AGENTS.md` ของเรามีกฎอย่างเช่น (ย่อจากไฟล์จริง)

```text
Reply to the owner in Thai.
Never read or print .env files or secret values.
High-risk code (payments, enrollment, migrations)
is merged by the owner, not the agent.
```

agent อ่านไฟล์นี้ทุกครั้งที่เริ่มงาน เราจึงไม่ต้องย้ำซ้ำ และเมื่อเจอปัญหาใหม่ เราเพิ่มกฎลงไฟล์นี้ แทนการหวังว่าจะจำได้เองครั้งหน้า

</Callout>

## ข้อผิดพลาดที่พบบ่อย

1. **บอกวิธี แต่ไม่บอกเป้าหมาย** เช่น "ใช้ React ทำปุ่ม" แต่ไม่บอกว่าปุ่มนี้มีไว้ทำอะไร agent จึงตัดสินใจเรื่องอื่นผิดทาง
2. **ไม่มีเกณฑ์รับงาน** สุดท้ายรู้ไม่ได้ว่างานเสร็จหรือยัง
3. **รวมหลายเรื่องไว้ในโจทย์เดียว** แก้บั๊ก เพิ่มฟีเจอร์ และเปลี่ยนสีในคราวเดียว ถ้าพังจะไม่รู้ว่าพังเพราะอะไร
4. **ใส่รหัสผ่านหรือ API key ลงในโจทย์** ห้ามเด็ดขาด ข้อความในโจทย์อาจถูกบันทึกเก็บไว้ ดู <ChapterLink number={9} />
5. **เชื่อคำว่า "เสร็จแล้ว" ของ agent** ตรวจตามเกณฑ์รับงานเองทุกครั้ง ดู <ChapterLink number={7} />
