# Spec (ร่าง): ประวัติรายสมาชิกในหน้าผู้ใช้ (งาน D)

วันที่ร่าง: 2026-10-02

สถานะ: **ร่าง รอการตัดสินใจ ยังไม่ได้เริ่ม implementation** (คำถามข้อ 1 และ 3 ด้านล่าง) มาจากข้อ D ของ [backlog งานหลังบ้าน](../admin-operations-backlog-2026-09-13.md) ตรวจเทียบ source บน `master` ณ `9dc9133` (บั๊กความคืบหน้าแก้แล้วใน #132 หลังจากนั้น) ใช้คำศัพท์สมาชิก ผู้ซื้อ และผู้เรียนตาม CONTEXT.md ของ repo

## ผลตรวจ source (อ่านโค้ดเท่านั้น ยังไม่ได้ลองใน browser หรือกับข้อมูลจริง)

**หน้าผู้ใช้ปัจจุบัน** แสดงข้อมูลบัญชี รายการลงทะเบียนเรียนพร้อมความคืบหน้า และปุ่มเพิ่ม/ลบการลงทะเบียน ไม่มีประวัติการชำระเงิน ไม่มีไทม์ไลน์การเปลี่ยนแปลง ผู้ตรวจต้องสลับไปหน้า Payments และ Audit logs เพื่อตอบเคส "ซื้อแล้วเข้าเรียนไม่ได้"

**ข้อมูลที่มีอยู่จริงสำหรับสร้างประวัติ**

| แหล่ง | ครบแค่ไหน | หมายเหตุ |
| --- | --- | --- |
| ตาราง `payments` | ครบ: วิธีชำระ ยอด สถานะ รายการ เวลา | ดึงตามผู้ใช้ได้ตรงๆ มี index `user_id` |
| audit ของ payment | มีเมื่อแอดมินเปลี่ยนสถานะ/อนุมัติ/ปฏิเสธ พร้อมเหตุผล | ผูกด้วย `entity_id` = payment id การเติมเต็มอัตโนมัติจาก Stripe/PromptPay ไม่แน่ใจว่าเขียน audit (ยังไม่ได้ตรวจ) |
| audit ของ enrollment | มีเฉพาะเมื่อแอดมินเพิ่ม/ลบ | `entity_id` เป็น enrollment id ไม่ใช่ผู้ใช้ ตัวผู้ใช้อยู่ในข้อความ `user: <id>, course: <id>` ต้องค้นด้วยข้อความ |
| audit ของบัญชี (`entity_type = 'user'`) | มีสำหรับ lifecycle (ปิด/เปิดใช้งาน ฯลฯ) และรีเซ็ตรหัสผ่าน | `entity_id` = id ผู้ใช้ ค้นตรงได้ |
| ตาราง `enrollments` | สถานะปัจจุบันเท่านั้น | ไม่มีคอลัมน์สถานะ ไม่มีเวลาถอน |

**ช่องว่างที่ต้องรู้**

1. การถอนสิทธิ์เรียนปัจจุบันคือ **ลบแถว enrollment จริง** ไม่ใช่ระงับ ซึ่งต่างจากนิยามใน CONTEXT.md ที่ว่าการถอนสิทธิ์ "เก็บประวัติและความคืบหน้าไว้ ให้สิทธิ์กลับแล้วเรียนต่อจากเดิมได้"
2. **พบบั๊กและแก้แล้ว:** route ลบ enrollment ลบความคืบหน้า (`lesson_progress`) ของผู้ใช้ **ทุกคอร์ส** ไม่ใช่เฉพาะคอร์สที่ถอน เพราะตารางนั้นมีแค่ `userId` กับ `lessonId` และ route กรองด้วย `userId` อย่างเดียว แก้ใน [#132](https://github.com/ohmiler/milerdev/pull/132) ให้ลบเฉพาะความคืบหน้าของบทเรียนในคอร์สที่ถอน ใน transaction เดียวกับการลบ enrollment ความคืบหน้าที่ถูกลบไปก่อนหน้านั้นกู้จากแอปไม่ได้ พฤติกรรมยังเป็นการลบแถวและลบความคืบหน้าของคอร์สนั้น ซึ่งยังต่างจากนิยามใน CONTEXT.md และต่างจากเส้นทางคืนเงินที่ลบ enrollment แต่เก็บความคืบหน้า
3. การเพิ่ม/ถอนสิทธิ์โดยแอดมินไม่มีช่องกรอกเหตุผล ประวัติจึงไม่มีเหตุผลสำหรับเหตุการณ์ประเภทนี้
4. `audit_logs` ไม่มี index บน `entity_type`/`entity_id` การค้นประวัติรายผู้ใช้จะสแกนตารางเมื่อข้อมูลมาก
5. การเติมเต็มอัตโนมัติจากการชำระเงิน (Stripe/PromptPay) สร้าง enrollment โดยไม่เขียน audit เลย ตรวจแล้วใน `payment-fulfillment` มีการเขียน audit เฉพาะการอนุมัติแมนนวล ประวัติของการซื้อปกติจึงมีแค่แถว payment เป็นหลักฐาน และการบอกว่า enrollment มาจากการชำระเงินเป็นการอนุมานจากการจับคู่ผู้ใช้กับรายการ ไม่ใช่บันทึกโดยตรง

## Problem Statement

เมื่อผู้ซื้อทักมาว่าซื้อแล้วเข้าเรียนไม่ได้ ผู้ดูแลระบบต้องเปิดหลายเมนูเพื่อประกอบเรื่อง ว่าชำระเงินเมื่อไร สถานะอะไร ใครเปลี่ยนสถานะเพราะอะไร ได้สิทธิ์เรียนหรือไม่ และใครให้หรือถอนสิทธิ์

## Solution

หน้าผู้ใช้มีส่วน "ประวัติ" ที่เรียงเหตุการณ์ของสมาชิกคนนั้นตามเวลา แยกให้ชัดว่าแต่ละเหตุการณ์เป็นเรื่องบัญชี การชำระเงิน หรือสิทธิ์เรียน แสดงผู้กระทำ เวลา และเหตุผลเมื่อมีหลักฐาน และบอกตรงๆ ว่า "ไม่มีข้อมูล" เมื่อไม่มี ไม่เดาย้อนหลัง

## User Stories

1. ในฐานะผู้ดูแลระบบ ฉันต้องการเห็นการชำระเงินทั้งหมดของสมาชิกพร้อมสถานะ ในหน้าผู้ใช้ เพื่อไม่ต้องไปค้นหน้า Payments
2. ในฐานะผู้ดูแลระบบ ฉันต้องการกดจากรายการชำระเงินไปยังเคสกระทบยอดหรือรายการนั้นได้ เพื่อดูรายละเอียดต่อ
3. ในฐานะผู้ดูแลระบบ ฉันต้องการเห็นว่าใครเปลี่ยนสถานะการชำระเงิน เมื่อไร และเพราะอะไร เพื่อตอบผู้ซื้อได้ถูกต้อง
4. ในฐานะผู้ดูแลระบบ ฉันต้องการเห็นว่าแต่ละการลงทะเบียนเรียนมีที่มาจากการชำระเงินหรือแอดมินเพิ่มเอง เมื่อมีหลักฐาน เพื่อเข้าใจว่าทำไมสมาชิกมีหรือไม่มีสิทธิ์
5. ในฐานะผู้ดูแลระบบ ฉันต้องการเห็นการเปิด/ปิดใช้งานบัญชี เพื่อแยกปัญหาบัญชีออกจากปัญหาการชำระเงินและสิทธิ์เรียน
6. ในฐานะผู้ดูแลระบบ ฉันต้องการให้เหตุการณ์เก่าที่ไม่มีบันทึกแสดงว่าไม่มีข้อมูล เพื่อไม่เข้าใจผิดว่าไม่มีเหตุการณ์เกิดขึ้น
7. ในฐานะผู้ดูแลระบบ ฉันต้องการให้ประวัติเป็นแบบอ่านอย่างเดียว เพื่อไม่มีใครให้สิทธิ์เรียนโดยบังเอิญจากการเปิดดู
8. ผู้ที่ไม่ใช่ผู้ดูแลระบบต้องเข้าถึงประวัติไม่ได้ (ตรวจสิทธิ์ฝั่งเซิร์ฟเวอร์)

## Implementation Decisions (ข้อเสนอ)

- **อ่านอย่างเดียว ไม่เปลี่ยน schema ในขั้นแรก** endpoint ใหม่ของผู้ใช้หนึ่งคนรวมสามแหล่ง: payments ของผู้ใช้, audit ของ payment เหล่านั้น, audit ของบัญชี (`entity_type = 'user'`) และ audit ของ enrollment ที่ข้อความระบุ id ผู้ใช้
- ส่งกลับเหตุการณ์ในรูปแบบเดียวกัน (ชนิด เวลา ผู้กระทำ ข้อความสรุป เหตุผลถ้ามี ลิงก์ไปเคส) เรียงใหม่ก่อน จำกัดจำนวนและแบ่งหน้า
- ไม่ส่ง IP หรือ user agent
- เหตุการณ์ที่ไม่มี audit ไม่ถูกสร้างขึ้นจากการคาดเดา แต่การชำระเงินที่สำเร็จคู่กับ enrollment ปัจจุบันแสดงได้ตามข้อเท็จจริงของตารางนั้น โดยไม่อ้างว่ามีบันทึกแอดมิน
- ส่วน UI ใช้องค์ประกอบ admin ที่มีอยู่ (ADR 0007) และใช้สถานะ โหลด/ผิดพลาด/ว่าง ที่แยกจากกัน ตามที่ทำในคิวกระทบยอด
- **ขั้นที่สอง (ต้องตัดสินใจแยก):** เหตุการณ์สิทธิ์เรียนแบบมีโครงสร้าง (ตารางเหตุการณ์ใหม่ หรือสถานะ enrollment) เพื่อให้ประวัติเป็นหลักฐานจริงและรองรับ "ถอนสิทธิ์เก็บความคืบหน้า" ตามนิยามใน CONTEXT.md ต้องมี migration จึงต้องถามก่อน

## Testing Decisions

- ทดสอบพฤติกรรมภายนอกของ endpoint (สิทธิ์แอดมิน, 404, การรวมและเรียงเหตุการณ์, การตัดฟิลด์เครือข่าย, ผู้ใช้ไม่มีข้อมูลเลย) ต่อยอดรูปแบบ mock ใน `tests/api/admin-reconciliation-case.test.ts`
- ทดสอบ component ของส่วนประวัติ: สถานะโหลด ผิดพลาด ว่าง และแสดงข้อความ "ไม่มีข้อมูล"
- mock Stripe, SlipOK, Bunny และอีเมลตามกติกา repo ไม่แตะข้อมูล production

## Out of Scope

- การแก้บั๊กลบความคืบหน้าทุกคอร์ส (งานแยก) และการเปลี่ยนความหมายของการถอนสิทธิ์เรียน
- การเพิ่มช่องเหตุผลในการเพิ่ม/ถอนสิทธิ์
- การสวมสิทธิ์ดูหน้าของผู้เรียน
- การแก้ไขสิทธิ์เรียนจากหน้าประวัติ
