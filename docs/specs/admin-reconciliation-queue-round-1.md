**เรื่องหลักฐานสลิป (ตรวจจาก source)**

- ผู้ซื้ออัปโหลดสลิป (JPG/PNG/WEBP ≤ 5MB) ระบบส่งต่อให้ SlipOK ตรวจ แล้วทิ้งไฟล์ ไม่ได้บันทึกที่ไหน
- รายการเข้าสถานะ `verifying` ตอนระบบจองรายการเพื่อเรียก SlipOK ถ้าหมดเวลา 30 วินาที ระบบตั้งใจเก็บรายการไว้ในสถานะนี้ให้ผู้ดูแลตรวจ (ข้อความถึงผู้ซื้อ: "ระบบจะเก็บรายการไว้เพื่อตรวจสอบ") ส่วนความล้มเหลวอื่นจะปล่อยรายการกลับ
- ดังนั้นสิ่งที่ผู้ตรวจใช้ตัดสินจริงคือ ยอดที่ควรได้รับ เวลา ผู้ชำระ และรายการเดินบัญชีธนาคารภายนอก ไม่ใช่รูปสลิป
- การอนุมัติแมนนวลไม่บันทึกเลขอ้างอิงธุรกรรมลงรายการ ทำให้ภายหลังไม่มีหลักฐานจากธนาคารผูกกับรายการ นอกจากเหตุผลใน audit

**ข้อค้นพบเพิ่มที่ backlog ยังไม่มี**

1. `days` ที่ไม่ใช่ตัวเลข (`?days=abc`) ทำให้ `parseInt` ได้ `NaN` วันที่กลายเป็น Invalid Date และคำสั่ง query น่าจะล้มเป็น 500 แทนที่จะเป็น 400 ยังไม่ได้ทดลองจริง
2. การปฏิเสธรายเดียวเพิ่ม `retryCount` และเมื่อถึง 5 ครั้งทั้งอนุมัติและปฏิเสธจะถูกปิด ส่วน bulk `mark_failed` ไม่เพิ่ม `retryCount` สองเส้นทางจึงให้ผลต่างกันกับสถานะเดียวกัน
3. คิวนี้ครอบคลุมเฉพาะ `method = promptpay` รายการ Stripe ไม่เข้าคิว (ตรงกับกฎ "Stripe ห้ามอนุมัติมือ")

## Problem Statement

ผู้ดูแลระบบที่ตรวจรายการ PromptPay ค้างเห็นเพียง 200 รายการล่าสุดภายใน 90 วัน แต่ตัวเลขสรุปนับรายการทั้งหมด จึงไม่รู้ว่ามีรายการค้างที่มองไม่เห็นอยู่ เมื่อกดเลือกทั้งหมดแล้วสั่ง bulk ระบบปฏิเสธโดยไม่บอกข้อจำกัดจริง และเมื่อโหลดล้มเหลวหน้าจออาจบอกว่า "ไม่พบรายการ" ซึ่งเป็นสัญญาณสำเร็จ ผู้ตรวจต้องสลับหน้าเพื่อหาข้อมูลผู้ชำระและยอดเงินก่อนตัดสินใจอนุมัติหรือปฏิเสธ ซึ่งเกี่ยวกับเงินและสิทธิ์เรียน และไม่มีรูปสลิปให้ตรวจเพราะระบบไม่เก็บ

## Solution

คิวกระทบยอดแสดงรายการค้างได้ครบโดยแบ่งหน้า มีค้นหาและมุมมองรายการค้างทุกช่วงเวลา เลือกได้ไม่เกินที่ระบบรับจริงและบอกข้อจำกัดชัดเจน แยกสถานะโหลด ผิดพลาด ว่าง และสำเร็จอย่างไม่ขัดกัน และให้ตรวจผู้ชำระ ยอดเงิน และข้อมูลประกอบ (รวมสถานะเลขอ้างอิงธุรกรรม) ในจุดตัดสินใจเดียวกันก่อนยืนยัน โดยไม่เปลี่ยนอำนาจอนุมัติ การสร้าง enrollment หรือ audit ที่มีอยู่

## User Stories

1. ในฐานะผู้ดูแลระบบ ฉันต้องการเลื่อนดูรายการค้างทั้งหมดทีละหน้าโดยไม่มีรายการซ้ำหรือหาย เพื่อไม่ให้เคสเก่าถูกมองข้าม
2. ในฐานะผู้ดูแลระบบ ฉันต้องการเห็นรายการที่รอนานที่สุดก่อน เพื่อจัดการเคสที่ผู้ซื้อรอนานก่อน
3. ในฐานะผู้ดูแลระบบ ฉันต้องการดูรายการค้างเกิน 90 วันได้ เพื่อไม่ให้เคสเก่าตกหล่นจากคิว
4. ในฐานะผู้ดูแลระบบ ฉันต้องการค้นหาด้วยเลขธุรกรรมหรืออีเมลผู้ชำระ เพื่อตอบเคสที่ผู้ซื้อทักมาโดยตรง
5. ในฐานะผู้ดูแลระบบ ฉันต้องการเห็นจำนวนที่กำลังแสดงเทียบกับทั้งหมด และขอบเขตของตัวเลขสรุป เพื่อรู้ว่าตัวเลขหมายถึงอะไร
6. ในฐานะผู้ดูแลระบบ ฉันต้องการให้การเลือกรายการไม่เกินจำนวนที่ระบบรับ และบอกเหตุผลเมื่อเกิน เพื่อไม่ส่งคำสั่งที่ถูกปฏิเสธโดยไม่ทราบสาเหตุ
7. ในฐานะผู้ดูแลระบบ ฉันต้องการให้การเปลี่ยนตัวกรองหรือหน้าล้างการเลือกอย่างถูกต้อง เพื่อไม่ส่งรายการที่ไม่ได้มองเห็น
8. ในฐานะผู้ดูแลระบบ ฉันต้องการเห็นข้อความผิดพลาดเมื่อโหลดล้มเหลว ไม่ใช่คิวว่าง เพื่อไม่เข้าใจผิดว่างานเสร็จ
9. ในฐานะผู้ดูแลระบบ ฉันต้องการรู้เมื่อข้อมูลที่เห็นเป็นข้อมูลเก่าหลังรีเฟรชล้มเหลว และไม่สามารถสั่งอนุมัติหรือปฏิเสธจากข้อมูลเก่าได้โดยไม่รู้ตัว
10. ในฐานะผู้ดูแลระบบ ฉันต้องการเห็นผู้ชำระ ยอดเงิน วิธีชำระ หลักฐาน และประวัติการตรวจของรายการในที่เดียวก่อนอนุมัติหรือปฏิเสธ เพื่อไม่จับคู่เคสผิด
11. ในฐานะผู้ดูแลระบบ ฉันต้องการให้ระบบบอกตรงๆ ว่ารายการมีเลขอ้างอิงธุรกรรมหรือไม่ และต้องเทียบกับรายการเดินบัญชีเมื่อไม่มี เพื่อตัดสินใจโดยไม่คาดว่ามีรูปสลิป
12. ในฐานะผู้ดูแลระบบ ฉันต้องการให้ระบบแจ้งเมื่อรายการถูกเปลี่ยนสถานะโดยผู้ตรวจอื่นระหว่างที่ฉันเปิดอยู่ เพื่อไม่อนุมัติซ้ำหรือทับกัน
13. ในฐานะผู้ดูแลระบบ ฉันต้องการให้ทุกการอนุมัติหรือปฏิเสธยังต้องระบุเหตุผลและถูกบันทึก audit เพื่อตรวจสอบย้อนหลังได้ (ไม่ลดทอนของเดิม)
14. ในฐานะผู้เยี่ยมชมหรือสมาชิกที่ไม่ใช่ผู้ดูแลระบบ ฉันต้องไม่เข้าถึงคิวหรือหลักฐานได้ (รักษาการตรวจสิทธิ์ฝั่งเซิร์ฟเวอร์)

## Implementation Decisions

**คำสั่งที่ยังเหมือนเดิม** — การอนุมัติยังผ่านการเติมเต็มการชำระเงินแบบแมนนวลเดิม (สร้างการลงทะเบียนเรียนในธุรกรรมเดียว) การปฏิเสธและ bulk ยังเขียนสถานะและ audit ในธุรกรรมเดียว บังคับเหตุผลอย่างน้อย 5 ตัวอักษร และตรวจสถานะปัจจุบันตอนเขียนเพื่อกันการชนกัน ไม่มีสิทธิ์เรียนเกิดจากการเปิดดูหลักฐาน

**A — รายการครบถ้วน**
- API รายการรองรับแบ่งหน้าฝั่งเซิร์ฟเวอร์ ส่งกลับจำนวนทั้งหมดของตัวกรองปัจจุบัน และใช้การเรียงที่เสถียรโดยมีตัวตัดสินเสมอ (วันที่แล้วตามด้วย ID)
- ค่าเริ่มต้นเรียงรายการที่รอนานที่สุดก่อนสำหรับสถานะที่เป็นงานค้าง
- เพิ่มตัวเลือกช่วงเวลา "ทั้งหมด" สำหรับรายการค้าง เพื่อให้เคสเกิน 90 วันเข้าถึงได้ ยังคงเพดาน 90 วันสำหรับมุมมองอื่นหากไม่ตัดสินใจเปลี่ยน
- เพิ่มค้นหาด้วยเลขธุรกรรมและอีเมลผู้ชำระ
- ตรวจสอบพารามิเตอร์ด้วย Zod (`status`, `days`, หน้า, คำค้น) ค่าที่ไม่ถูกต้องตอบ 400 ไม่ใช่ 500
- ตัวเลขสรุปต้องระบุขอบเขตเดียวกับรายการที่แสดงอย่างชัดเจน

**B — ข้อมูลก่อนตัดสินใจ (ปรับตามผลตรวจ: ไม่มีรูปสลิปให้แสดง)**
- ผู้ตรวจเห็นผู้ชำระ (ชื่อ อีเมล) ยอดเงิน (THB เป็นสตริงที่ขอบเขต DB) วิธีชำระ รายการ เวลาสร้างและจำนวน retry และประวัติการตรวจจาก audit ที่มีอยู่ ใน flow เดียวกับปุ่มอนุมัติ/ปฏิเสธ
- แสดงสถานะหลักฐานตามจริง: มีเลขอ้างอิงธุรกรรม หรือ "ระบบไม่เก็บรูปสลิป ให้เทียบกับรายการเดินบัญชี" แทนที่จะมีช่องหลักฐานว่างๆ
- ไม่แสดงหรือบันทึก log เนื้อหาสลิป และไม่ส่ง secret ไปฝั่ง client
- ประวัติการตรวจแสดงเฉพาะที่มีใน audit จริง รายการเก่าที่ไม่มี audit แสดงว่าไม่มีข้อมูล
- ถ้าต้องการให้เก็บเลขอ้างอิงธนาคารตอนอนุมัติแมนนวล ต้องเพิ่มช่องกรอกและเขียนผ่านเส้นทางอนุมัติเดิม (ดูคำถามข้อ 5)

**C — Bulk และสถานะโหลด**
- เพดานการเลือกเท่ากับเพดานของ bulk API (50) และขนาดหน้าเริ่มต้นเท่ากัน เพื่อให้ "เลือกทั้งหมด" หมายถึงทั้งหน้า
- แสดงข้อความชัดเจนเมื่อถึงเพดาน
- ไม่แบ่งส่งหลายชุดเพื่อเลี่ยงเพดาน เพราะจะเปลี่ยนความเป็น atomic ของ bulk โดยไม่บอก (ตามข้อกำหนดใน backlog)
- แยกสถานะ loading / error / empty / success ให้ไม่ซ้อนกัน โหลดล้มเหลวไม่แสดง empty state
- ล้างการเลือกเมื่อเปลี่ยนตัวกรอง หน้า หรือเมื่อโหลดล้มเหลว
- ข้อมูลเก่าหลังรีเฟรชล้มเหลวต้องระบุว่าเป็นข้อมูลเก่า และการสั่ง action ใช้การตรวจสถานะตอนเขียนเดิมเป็นด่านสุดท้าย

**การแบ่ง PR (ตาม AGENTS.md: งานเงินแยก PR เล็ก)**
1. C: UI honesty ไม่แก้สัญญา API ยกเว้นข้อความ error
2. A: pagination, ค้นหา, มุมมองรายการค้าง พร้อมตรวจ `days`
3. B: รายละเอียดเคสและข้อมูลประกอบการตัดสินใจ (หลังตัดสินใจคำถามข้อ 5)

## Testing Decisions

- ทดสอบพฤติกรรมภายนอก ไม่ทดสอบโครงสร้าง component หรือ CSS
- **Route tests** (ต่อยอด `tests/api/admin-payment-security.test.ts`): pagination ไม่ซ้ำ/ไม่หายในข้อมูล 120 รายการ, เรียงลำดับเสถียรเมื่อวันที่เท่ากัน, ตัวกรองและคำค้น, `days` ไม่ถูกต้องตอบ 400, ผู้ที่ไม่ใช่แอดมินถูกปฏิเสธ, bulk 50 ผ่าน 51 ปฏิเสธ, ความขัดแย้งของ bulk ตอบ 409 โดยไม่เขียนบางส่วน
- **Component tests** (ต่อยอด `tests/components/admin-operations-ui.test.tsx`): โหลดครั้งแรกล้มเหลวไม่แสดง empty state, รีเฟรชล้มเหลวหลังโหลดสำเร็จระบุข้อมูลเก่า, เลือกทั้งหมดเมื่อมี 200 รายการไม่เกิน 50, เปลี่ยนตัวกรองล้างการเลือก, ข้อความสถานะเลขอ้างอิงทั้งกรณีมีและไม่มี
- **E2E**: ไม่เพิ่มในรอบนี้ ยกเว้นเมื่อแตะ flow ที่ `Required E2E` ครอบคลุมอยู่แล้ว (ตรวจก่อนเริ่ม PR B)
- Mock Stripe, SlipOK, Bunny และอีเมลตามกติกา repo ไม่แตะข้อมูล production

## Out of Scope

- ประวัติรายสมาชิก (D) และการป้องกันฟอร์มสร้างคอร์สสูญหาย (E)
- การเปลี่ยนกติกา retry (เพดาน 5 ครั้ง) หรือความไม่ตรงกันระหว่าง bulk กับการปฏิเสธรายเดียว (ดูคำถามข้อ 6)
- รายการ Stripe, การคืนเงิน, webhook, SlipOK
- การแก้ schema หรือ migration (ยังไม่พบว่าจำเป็น ยกเว้นเพิ่ม index ถ้าการค้นหาช้า ซึ่งต้องถามก่อน)
- การอนุมัติหลายชุดอัตโนมัติ, การ assign เคสให้ผู้ตรวจ, การแจ้งเตือนผู้ซื้อแบบใหม่
