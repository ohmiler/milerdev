## ที่มาและขอบเขตหลักฐาน

ผู้ใช้ขอประเมินว่าหลังบ้านควรปรับปรุงอะไรเป็นลำดับแรก แล้วขอเก็บรายละเอียดไว้ทำรอบหน้า เอกสารนี้เก็บผลตรวจโค้ดของ dashboard, payments, reconciliation, รายละเอียดผู้ใช้ และฟอร์มสร้างคอร์ส ไม่ใช่การตรวจหลังบ้านทุกเส้นทางหรือรายงานปัญหาที่พิสูจน์บน production แล้ว

- ไม่ได้ทดลองผ่าน browser ที่ล็อกอิน และไม่ได้เข้าถึงข้อมูล production

- เส้นทางกระทบยอดที่ตรวจมีการบังคับเหตุผลและเขียนสถานะพร้อม audit ใน transaction แล้ว ต้องรักษาพฤติกรรมเหล่านี้
- อ้างอิง [ADR 0007](adr/0007-brand-aligned-admin-operations-ui.md) และ [workflow](workflow/README.md) ก่อนออกแบบหรือแก้ไข
- ตรวจ source ปัจจุบันอีกครั้งก่อนเริ่ม เพราะข้อค้นพบอาจเปลี่ยนไปหลังวันที่บันทึก

## A — คิวกระทบยอดต้องเข้าถึงรายการค้างได้ครบ

**สิ่งที่พบ:** API จำกัด 200 รายการ เรียงใหม่ก่อน และจำกัดช่วงย้อนหลังสูงสุด 90 วัน ไม่มี pagination ขณะที่ summary นับรายการทั้งหมดในช่วงที่เลือก หน้า UI ไม่มีทางไปหน้าถัดไป

**ผลกระทบ:** เมื่อเกิน 200 รายการ เคสเก่าภายในช่วงอาจไม่ปรากฏในคิวนี้ และเคสเกิน 90 วันไม่เข้าเงื่อนไข แม้หน้า Payments อาจเป็นทางค้นหาอื่นได้ จึงไม่ควรตีความว่าข้อมูลถูกลบหรือเข้าถึงไม่ได้จากทั้งระบบ

**แนวทางเสนอ:** เพิ่ม pagination, ค้นหาเลขธุรกรรม, เรียงรายการรอนานก่อน และมุมมองรายการค้างทุกช่วงเวลา

**เกณฑ์รับเบื้องต้น:**

- ชุดข้อมูลจำลองมากกว่า 200 รายการเข้าถึงได้ครบโดยไม่มีรายการซ้ำ/หายระหว่างหน้าในข้อมูลที่ไม่เปลี่ยน
- มีทางค้นหาเคสค้างเกิน 90 วันตามนโยบายที่ตกลง
- แสดงจำนวนที่กำลังเห็นเทียบกับทั้งหมด และขอบเขต summary อย่างชัดเจน
- การเปลี่ยนตัวกรองจัดการ pagination และ selection อย่างถูกต้อง

**ต้องตกลง:** สถานะใดถือเป็นงานค้าง; ค่าเริ่มต้นเรียงตามอะไร; ใช้ pagination แบบใด; พฤติกรรมเมื่อมีรายการใหม่หรือสถานะเปลี่ยนระหว่างเปิดคิว

หลักฐาน: [API](../src/app/api/admin/reconciliation/route.ts), [หน้า reconciliation](../src/app/admin/reconciliation/page.tsx)

## B — รวมข้อมูลที่ต้องใช้ก่อนอนุมัติ/ปฏิเสธ

**สิ่งที่พบ:** หน้า reconciliation รับ `slipUrl` แต่ไม่แสดงหลักฐาน ส่วนหน้า Payments มีลิงก์ดูหลักฐาน กล่องยืนยัน reconciliation แสดงชื่อรายการและ ID แต่ยังไม่สรุปผู้ชำระ ยอดเงิน และหลักฐานในจุดตัดสินใจ

**แก้ไข 2026-10-02:** ตรวจเส้นทางสลิปแล้วพบว่าระบบไม่เก็บรูปสลิป (ส่งต่อให้ SlipOK แล้วทิ้ง) และ `slipUrl` ถูกเขียนเฉพาะตอนชำระสำเร็จโดยมีค่าเป็นเลขอ้างอิงธุรกรรม จึงไม่มีหลักฐานรูปให้แสดงสำหรับรายการในคิว งาน B ที่ส่งมอบจึงแสดงข้อมูลเคสและบอกให้เทียบรายการเดินบัญชีแทน

**ผลกระทบ:** ผู้ตรวจต้องสลับหน้าเพื่อหาข้อมูล เพิ่มโอกาสจับคู่เคสผิดหรืออนุมัติจากบริบทไม่ครบ

**แนวทางเสนอ:** รายละเอียดเคสที่รวมผู้ชำระ ยอดเงิน วิธีชำระ หลักฐาน ประวัติการตรวจ และสิทธิ์เรียน พร้อมการอนุมัติ/ปฏิเสธ

**เกณฑ์รับเบื้องต้น:**

- ผู้ตรวจตรวจสอบตัวตนรายการและหลักฐานที่มีอยู่ได้จาก flow เดียว
- แยกหลักฐานที่เปิดได้, reference, ไม่มีหลักฐาน และโหลดผิดพลาดอย่างชัดเจน
- ยืนยันผู้ชำระ ยอดเงิน และรายการก่อนส่งคำสั่ง พร้อมเหตุผล
- รักษา server authorization, validation, transaction, audit และการป้องกันคำสั่งซ้ำ/สถานะชนกัน
- ไม่แสดง secret หรือบันทึกเนื้อหาสลิปลง log

**ต้องตกลง:** ใช้หน้ารายละเอียดหรือ panel; แหล่งข้อมูลประวัติ; นโยบายเมื่อหลักฐานไม่มีหรือเข้าถึงไม่ได้ โดยไม่เปลี่ยนอำนาจการอนุมัติโดยปริยาย

หลักฐาน: [reconciliation](../src/app/admin/reconciliation/page.tsx), [Payments](../src/app/admin/payments/page.tsx), [คำสั่งตรวจรายการ](../src/app/api/admin/reconciliation/[paymentId]/retry/route.ts)

## C — ทำ bulk actions และสถานะโหลดให้ตรงกับความจริง

**สิ่งที่พบสองข้อ:**

1. UI เลือกทั้งหมดได้ถึง 200 รายการ แต่ schema ของ bulk API รับสูงสุด 50 รายการ จึงมีคำสั่งที่ UI เปิดให้ส่งแต่ API ปฏิเสธ
2. เมื่อโหลดครั้งแรกล้มเหลว `loadError` แสดง error แต่เงื่อนไขแสดงรายการยังเข้า empty state โทนสำเร็จเมื่อ array ว่างได้ ต้องยืนยันด้วย component test

**แนวทางเสนอ:** จำกัด/อธิบาย selection ให้สอดคล้องกับ API และแยก loading/error/empty/success เป็นสถานะที่ไม่ขัดกัน

**เกณฑ์รับเบื้องต้น:**

- ทดสอบเลือก 50, 51 และเลือกทั้งหมดเมื่อมี 200 รายการ
- ผู้ใช้ไม่สามารถส่งคำสั่งที่เกินเพดานโดยไม่ทราบข้อจำกัด
- โหลดล้มเหลวไม่แสดงข้อความว่าคิวว่างหรือสำเร็จ
- รีเฟรชล้มเหลวหลังเคยโหลดสำเร็จต้องระบุข้อมูลเก่า และจัดการ action อย่างชัดเจน
- ทดสอบ conflict ระหว่าง bulk mutation กับการเปลี่ยนสถานะจากอีกผู้ตรวจ

**ต้องตกลง:** จำกัด selection ที่ 50 หรือออกแบบการทำงานหลายชุด; ถ้าทำหลายชุดต้องกำหนด partial success/retry ก่อน ห้ามแบ่งส่งโดยเปลี่ยน atomicity เงียบ ๆ

หลักฐาน: [UI](../src/app/admin/reconciliation/page.tsx), [bulk schema และ transaction](../src/app/api/admin/reconciliation/route.ts)

## D — ประวัติรายสมาชิกสำหรับตอบเคสซื้อแล้วเข้าเรียนไม่ได้

**สิ่งที่พบ:** หน้ารายละเอียดผู้ใช้เน้นคอร์ส สิทธิ์เรียน และความคืบหน้า ยังไม่รวมประวัติชำระเงินกับการเปลี่ยนแปลงของแอดมินในหน้าเดียว

**แนวทางเสนอ:** เพิ่มประวัติที่เชื่อมการซื้อ การให้/ถอนสิทธิ์ และเหตุผลของการเปลี่ยนแปลง โดยแยกสถานะบัญชี การชำระเงิน และสิทธิ์เรียน

**เกณฑ์รับเบื้องต้น:**

- ดู payment และ enrollment ที่เกี่ยวข้องจากผู้ใช้หนึ่งรายได้ พร้อมลิงก์ไปเคส
- แสดงผู้กระทำ เวลา และเหตุผลเฉพาะที่มีหลักฐานรองรับ ไม่สร้างประวัติย้อนหลังจากการคาดเดา
- ข้อมูลเก่าที่ไม่มี audit แสดงเป็นไม่ทราบ/ไม่มีข้อมูล
- อ่านข้อมูลได้เฉพาะผู้มีสิทธิ์ตาม server policy; หน้าประวัติไม่ให้สิทธิ์เรียนเอง

**ต้องตกลง:** ขอบเขตประวัติและช่วงเวลา; รองรับ bundle/refund อย่างไร; ข้อมูลใดมีจริงใน schema/audit; ต้องเปลี่ยน schema หรือไม่

หลักฐาน: [รายละเอียดผู้ใช้](../src/app/admin/users/[id]/page.tsx)

**สถานะ 2026-10-02:** ร่าง spec แล้วที่ [specs/admin-member-history.md](specs/admin-member-history.md) ยังไม่เริ่ม implementation รอตัดสินใจว่าจะทำขั้นแรกแบบอ่านอย่างเดียวหรือไม่ และการถอนสิทธิ์เรียนควรเป็นแบบลบแถวหรือระงับ

## E — ป้องกันข้อมูลฟอร์มสร้างคอร์สสูญหาย

**สิ่งที่พบ:** ฟอร์มสร้างคอร์สเก็บข้อมูลใน React state และบันทึกผ่าน submit ในขอบเขต admin ที่ค้นยังไม่พบการเตือนออกจากหน้าหรือการกู้คืนร่าง ต้องทดลอง navigation/reload เพื่อยืนยันก่อนแก้

**แนวทางเสนอ:** เริ่มจากเตือนเมื่อมีข้อมูลไม่บันทึก แล้วพิจารณา autosave เป็นงานถัดไป

**เกณฑ์รับเบื้องต้น:**

- มีวิธีป้องกันการออกจากหน้าขณะมีการแก้ไขตามข้อจำกัด browser และ router
- ฟอร์มไม่เปลี่ยนหรือบันทึกสำเร็จแล้วไม่เตือนโดยไม่จำเป็น
- บันทึกล้มเหลวคงข้อมูลไว้ให้ลองใหม่
- ทดสอบการยกเลิก กลับรายการ และ reload; ถ้ามี draft recovery ให้ทดสอบการคืนร่างด้วย
- Autosave ถ้ามี ต้องไม่เผยแพร่คอร์สหรือเปลี่ยน lifecycle โดยอัตโนมัติ

**ต้องตกลง:** เตือนอย่างเดียวหรือกู้คืนร่าง; ที่เก็บร่าง อายุร่าง และการแยกบัญชี; ขอบเขตขยายไปฟอร์มแก้ไข/บทเรียน

หลักฐาน: [สร้างคอร์ส](../src/app/admin/courses/new/page.tsx)

**สถานะ 2026-10-02:** ส่งมอบใน [#131](https://github.com/ohmiler/milerdev/pull/131) เตือนก่อนออก (reload ปิดแท็บ และลิงก์ในแอป) ยังไม่ดักปุ่ม Back/Forward ไม่เก็บร่าง และยังไม่ครอบคลุมฟอร์มแก้คอร์ส บทเรียน หรือบล็อก

## วิธีหยิบต่อรอบหน้า

1. อ่านเอกสารนี้และตรวจ source ปัจจุบัน เลือกรอบ 1 หรือรายการที่ต้องการ
2. ใช้ `/grill-with-docs` ปิดคำถามสำคัญของรายการที่เลือก โดยไม่ต้องออกแบบทุกงานใน backlog พร้อมกัน
3. ใช้ `/to-spec` เมื่อพร้อมสรุปขอบเขต แล้วแยกเป็นงานที่ตรวจรับได้ใน GitHub Issues ของ `ohmiler/milerdev` พร้อม dependencies ตาม [ข้อกำหนด tracker](agents/issue-tracker.md)
4. ก่อนสร้าง issues ตรวจงานที่มีอยู่เพื่อลดการซ้ำ แล้วเชื่อม issue กลับมายังเอกสารนี้ ให้ GitHub เป็นแหล่งสถานะงานหลังเผยแพร่ tickets
5. เริ่ม implementation ราย issue ตาม workflow ของ repo พร้อม tests ที่จำลอง providers; การอนุมัติ production และ migrations ใช้กติกา AGENTS.md
