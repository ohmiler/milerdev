# พื้นฐานเว็บที่พร้อมให้คนใช้งานจริง: แหล่งอ้างอิงและเกณฑ์ตรวจรับ

ตรวจแหล่งข้อมูลวันที่ 13 กันยายน 2026 เอกสารนี้เป็นข้อมูลประกอบการวางงานและแชร์ความรู้ ไม่ใช่ผลรับรองว่า MilerDev ผ่านกฎหมายหรือมาตรฐานแล้ว

## Cookie banner จำเป็นทุกเว็บไหม

ไม่ควรสรุปว่า “มีคุกกี้ = ต้องมีปุ่ม Accept ทุกกรณี” ต้องรู้ก่อนว่าเก็บข้อมูลอะไร เพื่ออะไร และใช้ฐานกฎหมายใด PDPA มาตรา 19 วางหลักเรื่องความยินยอม ส่วนมาตรา 24 มีกรณีที่ประมวลผลโดยไม่อาศัยความยินยอม เช่น ความจำเป็นเพื่อปฏิบัติตามสัญญา การจัดหมวดว่าเป็นคุกกี้จำเป็นจึงต้องสอดคล้องกับการใช้งานจริง ไม่ใช่แค่ตั้งชื่อหมวดเอง ([PDPA มาตรา 19 และ 24](https://ratchakitcha.soc.go.th/documents/17082307.pdf))

ตัวอย่างการแยกหมวด: DGA อธิบายคุกกี้จำเป็นสำหรับการลงชื่อเข้าใช้และความปลอดภัย แยกจากคุกกี้วิเคราะห์และโฆษณา นี่เป็นตัวอย่างการใช้งานของหน่วยงาน มิใช่บทกฎหมายที่ยกเว้นคุกกี้ทุกชนิดในหมวดนั้น ([นโยบายคุกกี้ DGA](https://www.dga.or.th/document-sharing/pdpa/124449/))

**ข้อเสนอทางวิศวกรรมสำหรับ MilerDev:** สำรวจ cookies, localStorage, scripts, iframes และ requests ของผู้ให้บริการภายนอกก่อน หากเพิ่ม analytics/marketing ที่อาศัยความยินยอม ให้ปิดไว้ก่อนจนผู้ใช้เลือกยอมรับ มีปฏิเสธส่วนเสริม ตั้งค่ารายหมวด และถอนความยินยอมได้ การมี banner อย่างเดียวไม่ได้ยืนยันว่า tracker ถูกบล็อกแล้ว ข้อเสนอนี้ไม่ได้นำกฎหมาย EU/UK มาใช้แทนกฎหมายไทย

## Privacy notice และการใช้สิทธิ

มาตรา 23 กำหนดรายละเอียดที่ต้องแจ้งก่อนหรือขณะเก็บข้อมูล เช่น วัตถุประสงค์ ข้อมูลที่เก็บ ระยะเวลา ผู้รับข้อมูล ผู้ควบคุมข้อมูลและช่องทางติดต่อ รวมถึงสิทธิของเจ้าของข้อมูล มาตรา 19 และ 30–36 ครอบคลุมการถอนความยินยอม เข้าถึง โอน คัดค้าน ลบ ระงับ และแก้ไขข้อมูล โดยแต่ละสิทธิมีเงื่อนไข จึงไม่ควรสัญญาว่า “ลบข้อมูลทุกอย่างทันที” โดยไม่พิจารณาภาระที่ต้องเก็บ ([PDPA มาตรา 19, 23, 30–36](https://ratchakitcha.soc.go.th/documents/17082307.pdf))

- [ ] กำหนด retention และการลบ/ทำให้ไม่ระบุตัวบุคคลเป็นงานปฏิบัติจริง
- [ ] แยกการรับทราบ notice/เงื่อนไขบริการออกจากความยินยอมการตลาด

## Accessibility: ทุกคนใช้งานเส้นทางสำคัญได้

ใช้ WCAG 2.2 ระดับ AA เป็นเป้าหมายคุณภาพที่เสนอ ไม่ใช่ข้อสรุปว่ากฎหมายไทยกำหนดมาตรฐานนี้กับเว็บทุกประเภท ตัวอย่างเกณฑ์ที่เกี่ยวข้องคือ keyboard (2.1.1), focus visible (2.4.7), focus not obscured (2.4.11), labels/instructions (3.3.2), contrast (1.4.3), reflow (1.4.10) และ captions สำหรับสื่อบันทึกล่วงหน้าตามเงื่อนไข (1.2.2) ([W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/))

- [ ] ใช้แป้นพิมพ์สมัคร เข้าสู่ระบบ ซื้อ และเปิดบทเรียนได้ เห็น focus และออกจาก dialog ได้
- [ ] ช่องกรอกมีชื่อ ข้อผิดพลาดเข้าใจได้ และ screen reader รับรู้สถานะสำคัญ
- [ ] ตรวจ contrast, zoom/reflow และคำบรรยายวิดีโอบทเรียน
- [ ] ตรวจด้วยคนร่วมกับเครื่องมืออัตโนมัติ ก่อนกล่าวอ้างว่าผ่าน WCAG

## Performance: วัดจากประสบการณ์ใช้งานจริง

Google ระบุ Core Web Vitals ที่ดีเป็น LCP ≤ 2.5 วินาที, INP ≤ 200 มิลลิวินาที และ CLS ≤ 0.1 โดยประเมิน percentile 75 และแยก mobile/desktop คะแนน Lighthouse หนึ่งครั้งจึงไม่เท่ากับผลผ่านจากผู้ใช้จริง ([Google Web Vitals](https://web.dev/articles/vitals?hl=en))

- [ ] วัดหน้ารายการคอร์ส รายละเอียดคอร์ส checkout และหน้าบทเรียนบนมือถือ
- [ ] ใช้ lab test หาจุดแก้ และ field data ยืนยันประสบการณ์จริงเมื่อมีข้อมูลเพียงพอ
- [ ] ถ้าข้อมูลผู้ใช้ยังไม่พอ ให้รายงานว่ายังวัดผลจริงไม่ได้ แทนการประกาศว่าผ่าน

## วิธีนำไปแชร์ต่อ

เล่าเป็นลำดับ “ปัญหาของผู้ใช้ → สิ่งที่ต้องตัดสินใจ → วิธีทำ → วิธีพิสูจน์” เช่น cookie consent ต้องแสดงหลักฐานว่า requests ถูกบล็อกก่อนยินยอม หรือ accessibility ต้องสาธิตเส้นทางซื้อด้วยแป้นพิมพ์ แยกให้ชัดระหว่างข้อกฎหมาย มาตรฐานคุณภาพ และข้อเสนอของทีม เอกสารนี้ครอบคลุมเฉพาะ privacy/cookies, accessibility และ performance; การตรวจระบบชำระเงิน ความปลอดภัย SEO และการกู้คืนระบบต้องทำเพิ่มเติม
